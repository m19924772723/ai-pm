## 任务 1：俞军《产品方法论》第 3 部分——交易与交易模型

### 核心概念

1. **产品是交易媒介**：企业通过产品与用户交换价值；交换的不是功能本身，而是功能背后的效用组合。
2. **交易模型**：一套能促成某种用户行为、并可持续的机制。不是“做出功能”，而是让各方都愿意持续参与。
3. **有利可图的用户价值**：用户价值不能脱离成本。免费、无广告、无限能力可能最讨好用户，却不一定可持续。
4. **相对价格**：`（直接成本 + 交易成本）÷ 效用组合`。增加效用或降低任一成本，都会降低用户的相对价格、提高需求。
5. **利益相关方**：设计交易前，先分别写清用户、提供方、平台/企业分别得到什么、付出什么。

### 用 L1 项目做一次交易模型拆解

| 角色 | 得到什么 | 付出什么 | 设计要点 |
|---|---|---|---|
| 学生/知识工作者 | 5000 字文章从约 30 分钟手动笔记缩短为“30 秒生成 + 3 分钟校对” | 粘贴/上传内容、核对结果、可能承担 API 成本 | 输出可追溯，避免用户核对成本高于节省时间 |
| 我（产品制作者） | 真实使用样本、评测数据、作品集证据 | 开发/调用成本、维护时间 | 先做单机 MVP，不做账号/云同步，控制成本 |
| 模型/API 提供方 | 调用费用 | 推理资源与稳定性责任 | 限制输入长度、记录失败并准备备用接口 |

**今天的理解：**
> “做一个摘要工具”不是产品价值；只有当用户节省的阅读/整理时间大于粘贴、等待和校对的成本，交易才会发生。L1 的关键指标不应只是“生成了”，而是“用户是否愿意复用”和“校对是否在 3 分钟内完成”。

**面试话术：**
> 我用交易模型审视 L1：用户得到的是结构化笔记和节省的时间，付出的是输入与校对成本。因此我没有把指标定成生成次数，而定成要点覆盖率、幻觉率、格式合规率和校对时间。先用本地 JSON 和单机 Streamlit 控制制作成本，等用户复用得到验证后再投入账号和云同步。

## 任务 2：Prompt Engineering Guide——进阶技巧的正确用法

### 核心概念

1. **CoT（思维链）适用于复杂推理**：将多步骤判断拆开，减少直接跳到结论的错误；不代表任何任务都应要求输出详细推理过程。
2. **少样本（few-shot）适用于格式或边界难以文字说清的任务**：先给输入→理想输出的示例，让模型模仿；L1 先用 Schema 约束，遇到边界案例再补 few-shot。
3. **一致性采样（self-consistency）以成本换稳定性**：同题多次生成、用投票选结果，更适合高风险或数理推理；L1 MVP 不做，避免调用成本翻倍。
4. **结构化输出优先于“文笔”**：产品接口首先要可解析、可展示、可评测；`JSON Schema + evidence` 是 L1 更重要的 prompt 技巧。
5. **提示词必须配评测**：单次“看上去不错”不等于可靠。后续用 20 条样本统计格式合规率、要点覆盖率、幻觉率。

### L1 的取舍

| 方法 | L1 v0.1 是否使用 | 原因 |
|---|---|---|
| System 指令 + JSON Schema | 使用 | 可控输出、便于程序解析与评测 |
| 原文 evidence | 使用 | 让每个结论可人眼核验，压制幻觉 |
| CoT 的最终结论式分步任务 | 按需使用 | 归档/摘要可要求按“主题→要点→待办”组织，但不展示冗长推理 |
| Few-shot | 暂不使用 | 没有真实失败样本前，不应虚构示例；Day 5 试跑后再决定 |
| Self-consistency | 不使用 | MVP 以低成本单次调用验证基本链路 |

## 收获 · 面试素材

> 我没有把“用了 CoT / RAG”当卖点。L1 的第一版只解决可控输出：固定 Schema、原文证据、信息不足留空。因为在长文结构化场景里，用户最在乎能不能核验和能不能直接使用；等 20 条评测集显示某类推理失败后，再针对性补 few-shot，而不是先堆技术名词。
