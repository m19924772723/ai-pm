## 项目线：问答链路（检索 → LLM 生成 → 引用校验）

### 新增模块（projects/L2-knowledge-base/query/）
- `llm_error.py` / `llm_utils.py`：复用 L1 端点表与纪律（密钥只读环境变量），
  **内置故障转移**（候选顺序循环 + fallback_from 记录 + warnings 可见）——L2 独立不 import L1
- `prompt.py`：QA 提示词。规则复用 L1 定案（quote 必须完整连续子串 / 输出固定中文 / JSON Schema 显式声明）
- `answer.py`：管线 = 检索 → 词面相关性把关（全无词面命中 → 拒答省一次 LLM）→ LLM → JSON → **引用校验** → QAAnswer
  - 引用校验：quote 必须是块文本的（空白归一化后）连续子串；chunk_id 接受"用户可见编号 1..k"与"内部名 chunk_0"两种（L1 教训：让模型写用户可见物，别逼它做翻译层）
  - 瞬态失败重试 1 次（含 JSON 解析失败——本次实际遇到并修好）

### 真实验证（4 问 × 3 轮迭代）
| 问题 | 结果 |
|---|---|
| 跨端点故障转移是做什么的 | ✅ 答案 + 5 条引用全过校验（doc/偏移可高亮）；fallback stepfun→deepseek→tuoji 自动转移可见 |

| 我今天中午应该吃什么 | ✅ 正确拒答（资料无关） |

### 本轮发现
1. **stepfun/deepseek 间歇性不可用比想象频繁**：两次 demo 里它们"失败→tuoji 兜底"；
   单测时刻又全 OK → 是瞬态，正因如此故障转移是必需品
2. **schema 不自洽被抓现行**：提示词用 [k] 编号，citations.chunk_id 却要 chunk_0 内部名 →
   模型按用户可见编号写 "1"、"4" → 校验全拒 → 修解析器接受两种形式
3. **JSON 解析失败也救得回**：deepseek 偶发非 JSON 输出 → 纳入重试循环（重试 1 次）→ 第三轮不再出现
