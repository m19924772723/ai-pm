# L1-1 项目启动说明书：长文 → 结构化

> 互联网产品阶梯 **第 1 级（L1 提示词级）** 的第一个项目
> 周期：**2 周**（研一上第 3–4 周，2026-10-06 ~ 10-19）
> 定位：**练手项目**——不计入正式作品集，但它的评测方法和踩坑记录会复用到 L2/L3
> 文件位置 `D:\code\hermes\ai_pm\`

---

## 1. 产品一句话

**贴一个链接或一段长文，输出结构化的摘要 + 关键点 + 标签 + 待办，可切模板、可一键导出 Markdown。**

## 2. 目标用户与场景

| 项 | 内容 |
|---|---|
| 用户 | 学生 / 知识工作者（你自己每天在痛：论文、公众号长文、报告） |
| 场景 | 读完一篇长文要写笔记、要提取待办、要归类归档 |
| 现状 | 手动读 + 手动记，一篇 5000 字文章要 30 分钟 |
| 目标 | 30 秒出结构化结果，自己再花 3 分钟校对 |

## 3. 为什么必须用 AI（面试必答，先想清楚）

- **"按需提取重点"是规则做不到的**：同一篇文章，有人要方法、有人要结论、有人要数据。模板写死就失效。
- **语义压缩不可规则化**：长文的核心信息散布在段落间，关键词提取只能得到"高频词"，得不到"结论"。
- **输出形态要随任务变化**：同一个输入，切"摘要模板"和切"待办模板"要出完全不同的结构。

> ⚠️ 这一节是 L1 唯一的"AI 必要性"论证。如果答不扎实，这个项目在面试里就是负分——所以上面三句要能张口就说。

## 4. 功能清单

### MVP（v1，必须做完）

| # | 功能 | 说明 |
|---|---|---|
| 1 | **三种输入** | ① 粘贴文本 ② 粘贴 URL（自动抓正文）③ 上传 PDF |
| 2 | **一次调用出结构化结果** | 输出 JSON：`{摘要, 关键点[], 标签[], 待办[]}` |
| 3 | **模板切换** | 摘要模式 / 待办模式 / 归档模式（三种不同字段组合） |
| 4 | **展示与导出** | 卡片式展示 + 一键复制 Markdown |

### v1 明确不做（写进作品集，这是加分项）

- ❌ 不做登录 / 多用户
- ❌ 不做云端历史同步（本地存即可）
- ❌ 不做批量处理
- ❌ 不做浏览器插件
- ❌ 不做多语言

> **为什么要显式写"不做什么"**：面试官最想看的是取舍过程。列出这 5 条，你就有话可讲。

## 5. 技术选型（按"2 周能出可交互 demo"来选）

| 层 | 选择 | 理由 |
|---|---|---|
| 交互界面 | **Streamlit**（Python） | 最快出可交互 demo，不用写前端；2 周能搞定 |
| 模型调用 | 你现有的中转 API（siyu 等），走 OpenAI 兼容接口 | 不用再申请；成本可控 |
| 结构化输出 | **JSON Schema / function calling** 强制结构化 | 直接练"输出可控性"这个 AI PM 核心能力 |
| URL 抓正文 | `trafilatura` 或 `readability-lxml` | 比正则干净，失败可降级为"请手动粘贴" |
| PDF 解析 | `PyMuPDF`（fitz） | 快、依赖少 |
| 存储 | 本地 JSON / SQLite | 不引入外部依赖 |

> **一条纪律**：用现成模型和框架，**不要自己训模型**。目标是产品跑通，不是技术炫技。

## 6. 两周排期（每天 1 个任务）

### 第 3 周（10-06 ~ 10-12）

| 天 | 任务 | 产出 |
|---|---|---|
| 1 | 环境搭好；API 跑通一次 hello world；确认成本 | 能调通 |
| 2 | 设计 JSON Schema；写提示词；跑通"文本 → 结构化 JSON" | 结构化输出可用 |
| 3 | 接三种输入（文本 / URL / PDF），做失败降级 | 输入层完成 |
| 4 | 三种模板 + 卡片展示 + 一键复制 Markdown | 交互完成 |
| 5 | 自己试用 10 篇真实长文，记录每个 bug 和卡点 | **踩坑日志** |
| 6 | 找 2 个同学试用，收反馈 | 反馈记录 |
| 7 | 按反馈修一版；复盘 | v0.2 |

### 第 4 周（10-13 ~ 10-19）

| 天 | 任务 | 产出 |
|---|---|---|
| 8 | 建评测集：**20 条**代表性样本（长短不一、中英混合、含表格的 PDF） | 评测集 |
| 9 | 人工标注每条的"标准关键点" | 标注完成 |
| 10 | 跑评测，算三个指标 | **第一版数字** |

| 14 | 写一页项目说明（问题 / 方案 / 取舍 / 数字 / 踩坑） | 项目说明 |

## 7. 评测方法（这一节比功能更重要）

| 指标 | 怎么算 | 目标 |
|---|---|---|
| **要点覆盖率** | 人工标注的关键点中，模型命中的比例 | 从 ~50% 提到 70%+ |
| **幻觉率** | 输出中出现原文没有的信息的比例 | 降到 5% 以下 |
| **格式合规率** | JSON 能一次解析成功的比例 | 95%+ |

> **为什么 L1 就要做评测**：这是你后面 L2/L3 评测体系的原型。而且面试时"我建了 20 条评测集，覆盖率从 50% 提到 72%，幻觉率从 12% 降到 4%"比"我做了个摘要工具"强一个量级。

## 8. 踩坑日志要记什么（面试素材来源）

每遇到一个问题就记一行：

```
问题：长文超过模型上下文，直接报错
怎么试的：先截断 → 结果丢结论；再分块摘要再合并
结果：分块+合并可用，但合并时要点重复
```

> **这份日志就是你回答"失败怎么排查"的弹药。** 面试官问到这里，别人只能说"我调试了一下"，你能说清试过哪几种方案、各自代价是什么。

## 9. 止损规则

| 情况 | 动作 |
|---|---|
| 第 3 周结束还没跑通"文本 → JSON" | 砍掉 URL 和 PDF，只保留粘贴文本 |
| URL 抓取失败率 > 40% | 直接砍掉 URL 输入，降级为"请手动粘贴" |
| 第 4 周还没出评测数字 | 评测集减到 10 条，先把数字做出来 |

> **宁可小而完整，不要大而残缺。** 2 周必须收尾，因为第 5 周要进 L2。

## 10. 做完之后：这个项目给你什么

| 收获 | 用到哪里 |
|---|---|
| 提示词工程 + 结构化输出的手感 | L2/L3 的地基 |
| **一套评测方法**（指标 + 评测集 + 失败分类） | L2/L3 直接复用，且是面试差异化武器 |
| 一份踩坑日志 | 回答"失败怎么排查" |
| "我能独立做出东西"的信心 | 支撑后面两级更难的阶梯 |

> ⚠️ **L1 太浅，不作为正式作品集案例。** 正式案例从 **L2** 开始。但 L1 的评测方法和踩坑日志要保留好——L2 会直接用到。
