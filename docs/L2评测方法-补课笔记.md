## 二、核心概念（每条都能回答「所以呢」）

1. **RAG 评估必须拆两半**：检索质量（找得准不准）+ 生成质量（答得好不好）。**检索质量是生成质量的上界**——检索丢了关键信息，生成再强也补不回来 → 所以优化永远先检索后生成。
2. **检索侧经典指标一组公式**：Precision@K = 前 K 里相关数/K；Recall@K = 前 K 覆盖的相关数/全部相关数；MRR = 第一个相关结果的倒数排名；NDCG = 位置加权（相关度随排名衰减）。手算例：gold 4 篇、Top-5 命中 3 篇 → P@5=0.6、R@5=0.75。
3. **RAGAS 把人工标注换成 LLM 判**：context precision（LLM 判相关性 + 排名越靠前加权越大）、context recall（gold 答案拆成 claims，看上下文撑住几个）。代价是每次评测烧 LLM 调用——**能离线验的绝不用线上预算验**。
4. **生成侧两个指标**：Faithfulness（答案每个 claim 都能被检索上下文支撑 = 反幻觉）+ Answer Relevancy（答的是不是问的，与检索内容无关）。
5. **评测方式三选一**：人工 gold 标注（准、贵、不可扩展）/ 规则判分（便宜、可离线、确定性，适合"逐字引用"这类硬约束）/ LLM-as-judge（可扩展、样板化；Langfuse 内置 hallucination / relevance / toxicity / correctness 模板，可对 trace 的单个 observation 打分）。**三种不是互替而是分层**：规则保底 → gold 校准 → judge 看趋势。

## 五、Langfuse 入门（本线只记概念，实操在 ai-agent U10）

- 定位：LLM 可观测性 + 评测一体化。**trace**（一次完整请求链，检索/生成各自成 span）、**session**（一次对话）、**user**（按账号归因成本与质量）、nested span（链不是单点）。
- 与评测的关系：LLM-as-judge 可以只挑 trace 里的 **retrieval 步骤**单独打相关性分（2026-02 起支持 observation 级），不用整条 trace 一起评——省 token 且定位准；离线则用 dataset 对每版 prompt 打分，过线才标 production。
- 接入成本：openai 分支替换一行 import 即可捕获调用；`@observe` 装饰器挂检索/生成函数即可建树。
- 落地分工：本线 W4 仅要求"入门（读到能讲清楚）"；把调用接进面板的实操是 ai-agent 线 U10 的单元验收，两边不重复做。

## 六、面试话术：Q12「一个 AI 功能效果不好，你怎么排查？」（题库第 12 题 · 今日书面首答）

> 拆链 + 真实案例。题库练习次数 0→1 记录于本笔记与 log（xlsx 面试题库 sheet 长期未同步，见 log 遗留）。

标准答法（拆链，从下往上）：
1. **定口径**：先确认"效果不好"到底指哪个数字、是真回归还是测量问题（评测集/指标定义有没有变）。
2. **按链拆**：输入质量 → 检索/上下文 → 提示词 → 模型选择 → 评测方法，每层一个可证伪动作。
3. **单变量验证**：一次只动一层，跑冻结评测集出前后对比数字。

我的真实案例（直接可讲）：L2 问答系统"引用准确率卡在 80% 上不去"。排查过程——先怀疑评测集标窄（分词/同义），rescore 排除；再定口径：检索 top-5 里 20 条 18 条 gold 都进了（召回 90%，"能找到"），但平均只有 1.5 块相关（**上下文相关性 30%，3.5 块是噪声**）——问题不在"能不能找到"，在"找到了筛不干净"。根因=混合检索 RRF 在全库算时词面强命中被稠密中等相关淹没（已经修成候选池保底）；下一层=Rerank 精排把 P@5 拉起来。**结论：数字先行归因，把"效果不好"拆成"哪个环节的哪个指标不好"，比拍代码试错快一个量级。**

## 七、一句话总结（能讲给面试官的）
「RAG 效果评估要拆检索/生成两半，检索质量是生成质量的上界；我的项目里『上下文相关性 30%』其实就是 Precision@5，这就是为什么我做 Rerank 而不是改提示词——因为问题出在找出来的一堆块里混了噪声，不在答。」
