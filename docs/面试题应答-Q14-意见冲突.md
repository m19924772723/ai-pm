# 面试题 Q14 应答：讲一次你和别人意见冲突怎么解决的（行为面 · 数据说服）

> 题库来源：`plans/AI产品经理求职计划表.xlsx` 面试题库 Q14（2026-10-16 周五刷题 1 道）。
> 考察点：协作、推动力——重点看你**怎么用数据/用户证据说服对方**，而不是谁吵赢。
> 素材：L2 知识库项目里一次真实发生的「结论冲突」——我用实测数据推翻了自己和工具链的初判。事件与数字全部来自 logs 与 commit，可复现，无虚构人物。
> 版本：书面首答；1.5 分钟版见末尾。诚实说明：目前可验证的冲突是「人与既有结论/工具链」的冲突，标准的「与同事意见分歧」故事待真实团队协作案例后替换（见文末【待填】）。

## STAR 正文（口述版）

**S 情境**：L2 项目评测（30 条问答集 + 检索指标）跑完，指标曲线是「好消息带一个坏消息」：召回 90%、但在纯向量检索下 Recall@5 = 0/10（Top1 是 ASCII 线框图）。当时的初判是「embedding 端点不可用 / 语料太生僻 / 检索方式不对」——我和我依赖的默认路线（稠密向量一把梭）出现了结论冲突：工具链的默认做法 VS 我要交付的结果。

**T 任务**：说服「按惯例继续调向量检索」这条路线站不住，落地一条更可靠的检索方案——前提是**证据先行，不能拍脑袋换方案**。

**A 动作**：
1. **先归因再动手**：不猜 embedding，先做诊断——用同样的 10 问评测集跑纯稠密，得到可复现数字（Recall@5 = 0/10），证明问题出在「检索范式」而不是「端点挂了」；
2. **量化对账**：对中文同域语料，稠密向量无法区分同主题近义段落（多一个"的"就判失败，12/13 压成 7/13 是匹配器问题，先修测量再谈系统）——把「感觉不行」变成「数字不行」；
3. **对照实验**：上混合检索（稠密 + 中文二元组 BM25 + RRF 融合）与纯稠密做同集对比，召回 0/10 → 90%；再用 20 条检索评测集锁死，事后补回归测试；
4. **用新结论推动路线**：把本次裁定（混合检索 + 二元组词面保底）写进方案文档和提示词，后续 W4 的 rerank 精排、查询改写都建在同一个评测集上——冲突的解法变成体系的一部分。

**R 结果**：检索召回拉到 90%→100%，P@5 55%（W4 口径），引用准确率 100%、MRR 0.71（2026-10-15 logs 实测）。**冲突从「工具链默认 vs 我的结果」变成「用数据选出的路线」，并且每次指标争论都有同一把尺子（评测集）可复现**。

## 为什么选这个故事

- 对齐 8 面试证据框架：解决了谁的问题（我要交付的作品集案例）/ AI 是否必要（检索是必要条件）/ 效果怎么衡量（30 条评测集 + 4 指标）/ 失败怎么排查（归因三件套）——一次冲突讲完四条。
- 冲突的本质不是人际关系，是**决策质量**：默认方案与目标结果的矛盾，用数据裁定而不是用职位或嗓门裁定——这正是 PM 岗位最想要的行为信号。
- 数字全部可复现（`projects/L2-knowledge-base/logs/retrieval_eval_w3.json`、`qa_eval_w4.json`）。

## 数据说服五步法（通用框架，来自本案）

1. **先归因**：冲突双方各说各的「原因」时，先列出可证伪的假设清单，逐条找证据排除；
2. **量化对账**：把「感觉 A 不行」翻译成「A 在某指标上是 X，目标 Y，差 Δ」——没有数字的对账没有意义；
3. **对照实验**：同一评测集上跑 A/B，只允许一个变量不同；
4. **先修尺子再修系统**：指标或评测集本身有偏差时（gold 标窄、匹配器误判），先修测量工具，否则动的每一步都在错误的尺子上做；
5. **事后固化**：验收标准、回归测试、方案文档同步更新，让这次裁定可复现、可复用。

## 1.5 分钟压缩版

「做 L2 RAG 检索时，纯向量检索在中文同域语料上 Recall@5 = 0/10，而按惯例它就是默认方案。我不猜原因是 embedding 挂了，而是先建 10 问检索评测集：同集对照混合检索（稠密 + 中文二元组 BM25 + RRF），召回拉回 90% 并锁成回归测试。冲突的解法不是换个人信我，而是换了把可复现的尺子——后面 W4 每一次优化（rerank、查询改写）都在同一评测集上验证。」

## 一句话素材

「跟默认路线冲突时，我不争『我的方案更好』，只做一件事：把两边的说法各自翻译成数字，在同一评测集上跑对照——输赢交给数据，而不是交给谁的声音大。」
