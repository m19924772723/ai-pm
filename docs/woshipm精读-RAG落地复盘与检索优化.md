## 一、核心论点

**RAG 上线容易优化难，生产级别更难。** 效果上限由数据质量决定，下限由检索效果决定；
80% 的效果问题靠优化数据与检索解决，不要一遇问题就换大模型。

## 二、检索优化六大坑（重点，逐条目对照我的 L2）

| # | 坑 | 作者的解法 | **我的 L2 现状对照** |
|---|---|---|---|
| 1 | **语义检索召回率不足**（核心经历找不到） | 分块原子化（500 字符/语义单元）+ 召回 Top10 + **问题标准化改写** | ⚠️ 半踩：我的"界面框架"题漏召回 = 同义改写问题，**未做查询改写** → 对应坑 1 的"问题改写环节缺失" |
| 2 | **检索精准度不足，上下文冗余 → 幻觉** | **Rerank 精排**（召回 Top10 → 精排取 Top3）+ 检索前/中/后三层防幻觉 | 🔴 **正中**：我今天测得上下文相关性仅 30%（top5 里 3.5 块是噪声）——正是他说的"低相关碎片混进上下文"；**没做 Rerank 是我最大的缺口** |
| 3 | 向量库选型盲目跟风（Milvus 拖垮落地） | 场景优先：小数据量选 FAISS 轻量库 | ✅ 已避险：我选 Chroma 论证过（数据量小/要元数据/持久化），他选 FAISS——结论一致"小体量用轻量库"，理由略不同 |

## 三、对我 L2 最有价值的 3 条（W4 优化清单）

### 1. Rerank 精排 → 直接治"上下文相关性 30%"
- 作者：召回 Top10 → rerank 精排 → 只留 Top3 高相关 → 过滤噪声给 LLM
- **我的现状**：search_all 直接给 top-5，噪声块进上下文 → 引用准确率被拖累
- **W4 行动**：加一个 rerank 层（轻量交叉编码器或 LLM 打分），量化对比排序前后上下文相关性
- 依据：我今天的数字——上下文相关性 30%（目标 60%），top5 里 3.5 块是噪声

### 2. 问题标准化改写 → 治"同义改写题漏召回"
- 作者：用户口语化提问 → 改写成与知识库匹配的标准化问题 → 再检索
- **我的现状**："L1 用了哪个界面框架？" 原文写"前端/UI Streamlit"——词面不重叠，检索漏
- **W4 行动**：查询改写（规则/LLM 二选一），在检索前把问题改写成本语化表达

### 3. "防幻觉核心在检索不在生成" —— 验证我的方向
- 作者：上下文越干净幻觉越低，别指望提示词挡脑补
- **我的现状**：已做"检索把关拒答"（无词面命中直接拒）+ 引用校验（quote 连续子串）——方向一致 ✅
- 他的"三层防线"（检索前规则/检索中只传高相关/生成后校验）可补充我的检索前层：预设敏感词规则

## 四、一句话收获

> **RAG 的坑集中在检索：召回看"分块+改写"，精准看"Rerank+过滤"——上下文越干净，幻觉越低。**
> 我今天测出上下文相关性 30%，正好印证坑 2：不是没召回，是召回里噪声太多。
> 下一步最该做的不是换 embedding，是**给 top-k 加一道精排**。

## 自测题

1. 为什么"召回 Top10 → 精排取 Top3"能同时保住召回率和精准度？（答：召回阶段放宽保证不漏，精排阶段收紧保证不脏，两阶段解耦）
2. 作者选 FAISS 而我选 Chroma，矛盾吗？（答：不矛盾，都是"小数据量用轻量库"；差别在需求——他要纯检索零运维，我需要元数据过滤+持久化，Chroma 自带；面试可讲）
3. "RAG 上线容易优化难"在你的项目里哪个数字印证？（答：上下文相关性 30%——检索能召回（90%）但噪声大（70% 无关块），优化空间在精排）
4. 防幻觉为什么核心在检索不在生成？（答：LLM 对上下文"天然信任"，给什么就信什么；给脏上下文它会把噪声脑补进答案，提示词只能约束输出格式，约束不了脑补的素材来源）
